1 Document Purpose & Consolidation Note

This is a single, self-contained Low-Level Design (LLD) document for the Bank Account Management System (BAMS). It merges the specifications across Phase 1 (Authentication & User Management), Phase 2 (Account Management & Ownership), Phase 3 (Financial Transactions & Concurrency), Phase 4 (Transaction History & Querying), Phase 5 (System Save & Restore / Backup & Rehydration), and Phase 6 (Production Hardening) into one coherent engineering contract, so it can be handed to an AI coding tool (or an engineer) with the instruction “implement exactly this” and produce a consistent, working, end-to-end codebase.

Two consolidation decisions were made while merging the source specifications:

  1. Single technology stack. The system standardizes on ASP.NET Core Web API (C# / .NET 8) + React 18 (Vite) + Microsoft SQL Server + Entity Framework Core 8. All database DDL, types, and constraints are written in SQL Server dialect (decimal(18,2), rowversion, datetime2, nvarchar).
  2. Implemented items only. Technologies and architectural patterns flagged as optional or unselected (e.g., Redis distributed caching, SignalR real-time hubs, Razor Pages, microservices, containerization) are omitted or categorized as not implemented to ensure an unambiguous contract for automated development.

This document specifies the AI Coding Execution Contract, a complete frontend page/route specification, field-by-field DTO contracts, database seed data, environment configurations, a Definition of Done checklist, literal request/response examples, frontend-to-backend permission mappings, testing matrices, and a ready-to-copy AI project generation prompt.

2 AI Coding Execution Contract

This section governs how any AI coding tool (or developer) must behave while building the BAMS from this document. It is binding for the entire build:

  1. Treat this document as the single source of truth. If something is not specified here, stop and flag it rather than inventing a convention silently.
  2. Do not change technology, architecture, entities, API contracts, roles, permissions, business rules, or database design without explicit approval.
  3. Do not generate placeholder implementations. No TODO, no NotImplementedException, no empty method bodies, no fake in-memory repositories standing in for real ones, no hard-coded mock API responses.
  4. Build the project incrementally, following the Build Order (§29.1) — one phase at a time, never the whole application in one pass.
  5. After completing each phase:
    • restore/install dependencies (backend and frontend)
    • compile the backend with 0 errors and 0 warnings
    • build the frontend
    • run the unit and integration tests for that phase
    • verify database migrations apply cleanly against SQL Server
  6. Do not proceed to the next phase if the current phase does not build or does not pass its tests.
  7. All backend API responses must use standard DTOs or structured envelopes — no endpoint returns a bare internal entity or exposes passwords/hashes.
  8. Never expose EF Core entities directly through controllers — every request/response crosses the API boundary as a DTO (§17.4, §18).
  9. Never bypass authorization — every endpoint carries the policy listed for it; no endpoint is left [AllowAnonymous] unless explicitly specified (only /api/v1/auth/register and /api/v1/auth/login).
  10. Never put business logic inside controllers — controllers route, validate models, and invoke services; balance calculations, account type constraints, and transfer validations live in the Service Layer.
  11. Never put database access directly inside controllers or React components — controllers depend on service interfaces; React components call centralized API client functions.
  12. Use dependency injection according to the architecture — all services are constructor-injected and registered with Scoped lifetime in Program.cs.
  13. Maintain optimistic concurrency using EF Core RowVersion on accounts to prevent balance race conditions.
  14. Generate all required tests listed in the Testing Matrix (§24) — a module is not done without verification.
  15. At completion, verify every item in the Final Acceptance Criteria (§27) before declaring the project finished.

3 Software Development Life Cycle (SDLC) Model

3.1 Model Selected: Waterfall

The BAMS project follows the Waterfall SDLC model. Requirements and architecture are completely determined up-front to deliver a secure financial platform:

Requirements -> System Design (this LLD) -> Implementation -> Integration & Testing -> Deployment -> Maintenance

3.2 Why Waterfall Is Suitable Here

  • Requirements are fully known and fixed up front. In banking, ledger accounting rules, cash-only savings constraints, and optimistic concurrency cannot drift mid-development.
  • Linear dependency-ordered build path. Identity & Auth must exist before Accounts; Accounts must exist before Transactions; Transactions must exist before Querying and Backup/Restore.
  • AI-Assisted single-pass execution. AI tools perform best against an unambiguous, fully specified contract without renegotiating requirements.
  • Strict acceptance gates. Financial software requires comprehensive verification against fixed criteria before production sign-off.

5 Architecture

5.1 Style

Clean Layered (N-Tier) Architecture deployed as a modular Web API backend paired with a decoupled React SPA client:

Layer Responsibility Concrete Examples
API Layer HTTP transport, route dispatching, model validation, Swagger AuthController, AccountsController, TransactionsController, SystemController
Middleware Layer Cross-cutting pipeline concerns, tracing, exceptions, telemetry CorrelationIdMiddleware, ExceptionMiddleware, RequestLoggingMiddleware
Service Layer Business rules, ACID transfer orchestration, concurrency checks AuthService, AccountService, TransactionService, SystemBackupService
Data Layer Entity modeling, database context, migration history ApplicationDbContext, Account, Transaction, ApplicationUser, Migrations
Client Layer User interface, client-side routing, JWT storage, state context React components, AuthContext, Axios instance, CSS Modules

5.2 Request Flow

React.js (Frontend SPA)
  | HTTPS Request (JSON) + Authorization: Bearer <JWT>
  v
Kestrel Web Server
  |
  +--> CorrelationIdMiddleware (Generates or propagates X-Correlation-ID)
  |
  +--> ExceptionMiddleware (Global try/catch: maps domain exceptions to 400/401/404/409/422/500)
  |
  +--> RequestLoggingMiddleware (Measures execution time with Stopwatch; logs method, path, status, ms)
  |
  +--> UseRateLimiter (Fixed-window limiter: max 10 requests/min on /auth/login)
  |
  +--> UseAuthentication (Validates JWT signature, lifetime, issuer, audience)
  |
  +--> UseAuthorization (Enforces role claims & endpoint access)
  v
Controller Layer (Model validation via [ApiController], route extraction)
  v
Service Layer (Business rules: Savings cash-only, active account check, ownership check)
  v
EF Core 8 / DbContext (LINQ, BeginTransactionAsync, RowVersion concurrency check)
  v
Microsoft SQL Server (Database: BankAccountDb)
  ^
  | Balance updated & Transaction record inserted
  +-- Result returned wrapped in DTO —> ExceptionMiddleware —> JSON Response

5.3 Module Boundaries

The system enforces modular boundaries across four primary business domains:

  • Authentication & User Management: Manages ApplicationUser, Identity roles (Admin, User), registration, login, and JWT generation.
  • Account Management: Manages bank accounts, account number formatting (ACC-YYYYMMDD-XXXX), ownership validation, and soft deactivation (IsActive = false).
  • Transaction Management: Executes deposits, withdrawals, and atomic transfers. Enforces Savings cash-only constraint, Checking cheque support, balance sufficiency, and optimistic concurrency checks.
  • System Backup & Rehydration: Admin-only module providing full database export to JSON and atomic transactional rehydration.

9 Database Design — Indexes & Constraints (SQL Server)

Foreign keys enforce ON DELETE RESTRICT / NO ACTION to guarantee that banking ledgers remain immutable and cannot be orphaned. Concurrency is handled by SQL Server’s native rowversion data type.

-- Unique index on account numbers
CREATE UNIQUE NONCLUSTERED INDEX [IX_Accounts_AccountNumber]
ON [Accounts]([AccountNumber]);

-- Unique index on employee codes
CREATE UNIQUE NONCLUSTERED INDEX [IX_AspNetUsers_EmployeeCode]
ON [AspNetUsers]([EmployeeCode]);

-- Unique index on financial transaction reference numbers
CREATE UNIQUE NONCLUSTERED INDEX [IX_Transactions_ReferenceNumber]
ON [Transactions]([ReferenceNumber]);

-- Performance index for global chronological sorting
CREATE NONCLUSTERED INDEX [IX_Transactions_TransactionDate]
ON [Transactions]([TransactionDate]);

-- Composite index optimizing account-specific historical queries
CREATE NONCLUSTERED INDEX [IX_Transactions_AccountId_TransactionDate]
ON [Transactions]([AccountId], [TransactionDate]);

Design benefits of this schema:

  • Audit trail immutability: Soft delete prevents physical deletion of accounts that have transaction rows attached.
  • Race condition prevention: The RowVersion column increments on every SQL UPDATE, allowing EF Core to identify concurrent writes and throw DbUpdateConcurrencyException.
  • High-speed ledger pagination: The composite index on (AccountId, TransactionDate) provides sub-millisecond query performance on paginated history lookups.

13 Authentication — JWT Contract

13.1 Claims in the Access Token

{
  "http://schemas.xmlsoap.org/ws/2005/05/identity/claims/nameidentifier": "usr_99182",
  "http://schemas.xmlsoap.org/ws/2005/05/identity/claims/emailaddress": "customer@bank.com",
  "http://schemas.microsoft.com/ws/2008/06/identity/claims/role": "User",
  "employeeCode": "EMP042",
  "jti": "c89f2a0b-11d2-4e8c-8f43-098274aef12a",
  "iss": "BankAccountManagementSystem.API",
  "aud": "BankAccountManagementSystem.Client",
  "exp": 1735142400
}
  • Token Algorithm: HMAC-SHA256 (SecurityAlgorithms.HmacSha256) with a 256-bit symmetric key.
  • Access Token TTL: 60 minutes (configurable via JwtSettings.ExpiryInMinutes).
  • Clock Skew: Set to TimeSpan.Zero for exact expiration enforcement.

13.2 Endpoints

Method Route Payload Response
POST /api/v1/auth/register RegisterRequest (EmployeeCode, Names, Email, Password) 201 Created — RegisterResponse
POST /api/v1/auth/login LoginRequest (Email, Password) 200 OK — LoginResponse (Token, User Profile)

13.3 Password Policy & Lockout

  • Password Constraints: Minimum 8 characters; must contain at least 1 digit, 1 lowercase letter, 1 uppercase letter, and 1 non-alphanumeric character.
  • Hashing: PBKDF2 with HMAC-SHA256 and cryptographic per-user salt.
  • Lockout Policy: 5 consecutive failed access attempts triggers a 5-minute account lockout.

13.4 Middleware Pipeline Order (Program.cs)

The middleware pipeline executes in strict sequential order:

1. CorrelationIdMiddleware   --> Assigns or propagates X-Correlation-ID
2. ExceptionMiddleware       --> Global catch: formats standard JSON error envelope
3. RequestLoggingMiddleware  --> Telemetry: logs method, path, status, duration (ms)
4. UseSwagger & SwaggerUI   --> Development API documentation
5. UseHttpsRedirection       --> Enforces HTTPS transport
6. UseStaticFiles            --> Serves static assets
7. UseRouting                --> Resolves endpoint routing
8. UseRateLimiter            --> Enforces fixed-window limiter on /auth/login
9. UseAuthentication         --> Validates JWT Bearer token
10. UseAuthorization         --> Enforces role and policy authorization
11. MapHealthChecks          --> GET /health endpoint
12. MapControllers           --> Dispatches request to controller action

17.2 Example Service Method (TransferAsync: ACID + Concurrency + Logging)

public async Task<TransactionResponse> TransferAsync(TransferRequest request, string userId, bool isAdmin)
{
    if (request.SourceAccountId == request.DestinationAccountId)
        throw new InvalidTransactionException("Source and destination accounts must be different.");

    using var dbTx = await _context.Database.BeginTransactionAsync();
    try
    {
        var source = await _context.Accounts.FirstOrDefaultAsync(a => a.AccountId == request.SourceAccountId)
                     ?? throw new KeyNotFoundException("Source account not found.");
        var dest = await _context.Accounts.FirstOrDefaultAsync(a => a.AccountId == request.DestinationAccountId)
                   ?? throw new KeyNotFoundException("Destination account not found.");

        // Validate active state
        if (!source.IsActive) throw new AccountInactiveException(source.AccountNumber);
        if (!dest.IsActive) throw new AccountInactiveException(dest.AccountNumber);

        // Validate ownership
        if (source.UserId != userId && !isAdmin)
            throw new UnauthorizedAccessException("Access denied to source account.");

        // Business Rule: Transfers only permitted between Checking accounts
        if (source.AccountType != AccountType.Checking || dest.AccountType != AccountType.Checking)
            throw new InvalidAccountTypeException("Transfers are only permitted between Checking accounts.");

        // Validate balance sufficiency
        if (source.Balance < request.Amount)
            throw new InsufficientBalanceException(source.Balance, request.Amount);

        source.Balance -= request.Amount;
        dest.Balance += request.Amount;

        var refNumber = GenerateReferenceNumber();

        var debitTx = new Transaction {
            AccountId = source.AccountId,
            RelatedAccountId = dest.AccountId,
            Amount = request.Amount,
            TransactionType = TransactionType.Transfer,
            TransactionMode = request.Mode,
            Status = TransactionStatus.Completed,
            ReferenceNumber = refNumber,
            TransactionDate = DateTime.UtcNow,
            Description = $"Transfer to {dest.AccountNumber}"
        };

        var creditTx = new Transaction {
            AccountId = dest.AccountId,
            RelatedAccountId = source.AccountId,
            Amount = request.Amount,
            TransactionType = TransactionType.Transfer,
            TransactionMode = request.Mode,
            Status = TransactionStatus.Completed,
            ReferenceNumber = refNumber,
            TransactionDate = DateTime.UtcNow,
            Description = $"Transfer from {source.AccountNumber}"
        };

        _context.Transactions.AddRange(debitTx, creditTx);
        await _context.SaveChangesAsync();
        await dbTx.CommitAsync();

        _logger.LogInformation("Transfer completed: {RefNumber}, Amount: {Amount}, From: {From}, To: {To}",
            refNumber, request.Amount, source.AccountNumber, dest.AccountNumber);

        return MapToResponse(debitTx, source.Balance);
    }
    catch (DbUpdateConcurrencyException ex)
    {
        await dbTx.RollbackAsync();
        _logger.LogWarning(ex, "Concurrency violation during transfer.");
        throw;
    }
    catch
    {
        await dbTx.RollbackAsync();
        throw;
    }
}

19 Financial & Transaction Engine — Deep Detail

19.1 Balance & Transaction Formulas

Deposit:
  New Balance = Current Balance + Deposit Amount

Withdrawal:
  New Balance = Current Balance - Withdrawal Amount
  Constraint: Current Balance >= Withdrawal Amount (else throw InsufficientBalanceException)

Transfer:
  Source New Balance = Source Current Balance - Transfer Amount
  Destination New Balance = Destination Current Balance + Transfer Amount
  Constraint: Source Current Balance >= Transfer Amount
  Constraint: Source.AccountType == Checking AND Destination.AccountType == Checking

19.2 Transfer Processing Flow

Client POST /api/v1/transactions/transfer
  |
  v
Validate Request Model (Source != Destination, Amount > 0)
  |
  v
Begin EF Core Database Transaction (await _context.Database.BeginTransactionAsync())
  |
  +-- Fetch Source Account (Include RowVersion)
  +-- Fetch Destination Account (Include RowVersion)
  |
  v
Check Active Status (Both accounts must have IsActive == true)
  |
  v
Check Ownership (Caller must own Source Account or hold Admin role)
  |
  v
Enforce Account Types (Both accounts must be Checking; Savings cannot transfer)
  |
  v
Verify Balance Sufficiency (Source Balance >= Amount)
  |
  v
Update Balances (Source -= Amount; Destination += Amount)
  |
  v
Create Transaction Ledgers (Debit leg with RelatedAccountId; Credit leg with RelatedAccountId)
  |
  v
Commit Changes (SaveChangesAsync -> CommitAsync)
  | If DbUpdateConcurrencyException occurs -> RollbackAsync -> Throw Conflict (409)
  | If any error occurs -> RollbackAsync -> Throw Exception
  v
Return TransactionResponse

19.3 Concurrency Control & RowVersion Mechanics

Financial transactions are highly susceptible to lost updates if two requests read the same balance and update it concurrently. BAMS implements Optimistic Concurrency Control using SQL Server’s rowversion column:

  • Account.RowVersion is mapped in EF Core using entity.Property(a => a.RowVersion).IsRowVersion().
  • SQL Server automatically increments the rowversion value whenever an account record is updated.
  • EF Core appends WHERE AccountId = @id AND RowVersion = @original to the SQL UPDATE statement.
  • If another thread modified the balance first, zero rows are affected, causing EF Core to throw DbUpdateConcurrencyException.
  • ExceptionMiddleware catches this exception and returns an HTTP 409 Conflict response, advising the client to retry.

23 Security, Exception Handling & Production Hardening

23.1 Exception Handling Contract

ExceptionMiddleware catches all downstream exceptions and translates them into uniform, sanitized JSON responses:

public async Task InvokeAsync(HttpContext context)
{
    try { await _next(context); }
    catch (Exception ex) { await HandleExceptionAsync(context, ex); }
}

private async Task HandleExceptionAsync(HttpContext context, Exception ex)
{
    var statusCode = ex switch
    {
        DbUpdateConcurrencyException => 409,
        UnauthorizedAccessException  => 401,
        KeyNotFoundException         => 404,
        ArgumentException            => 400,
        InvalidOperationException    => 422, // InsufficientBalance, AccountInactive, InvalidAccountType
        _                            => 500
    };

    var message = _env.IsDevelopment() ? ex.Message : "Something went wrong. Please try again later.";
    // Returns { success = false, message, statusCode, correlationId }
}

23.2 Security Design

  • Authentication: Signed JWT tokens containing user claims, role claims, and 60-minute expiration.
  • Brute-Force Protection: Fixed-window rate limiting on login restricts requests to 10/min per remote IP.
  • SQL Injection Defense: EF Core parameterizes all queries; raw concatenated SQL is prohibited.
  • Account Ownership Validation: Normal users are strictly restricted to inspecting and transferring from accounts matching their own ClaimTypes.NameIdentifier.
